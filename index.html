Conversation من جوه

في الشات، أنت عندك حاجات لازم تفرق بينهم من أول يوم:

Open / Pending / Snoozed / Resolved

Open يعني شغالة. Pending معناها مستنية. Snoozed مؤجلة لوقت لاحق. Resolved اتقفلت.

Reply vs Private Note

Reply للعميل. Private Note للفريق الداخلي فقط. غلطة صغيرة هنا ممكن تبوظ تجربة العميل.

Assignee / Team

مين ماسك المحادثة؟ موظف محدد ولا Team؟ خلي الفرق ده واضح عندك لأنه أساس الـ Routing.

Labels / Priority

Label بيديك تصنيف، وPriority بتديك أولوية. الاتنين مهمين في الـ Filtering والAutomation والتقارير.

💡 فكر زي مدير خدمة عملاء

لما العميل يقول “فين الطلب؟” مش أول سؤال تسأله “أحط Label إيه؟”. الأول افهم المشكلة: هل دي متابعة؟ شكوى؟ طلب تعديل؟ وبعدين صمّم الـ workflow اللي يخلي النوع ده يتحرك لوحده.

افتح Conversationsابدأ بـ Unassigned أو Mine وشوف الفرق.
افتح Conversation تجريبيةحدد العميل، الـ Inbox، الـ Assignee، والـ Status.
اكتب Replyبعدها جرّب Private Note واعمل @Mention لزميل.
جرّب Snooze ثم Resolveلاحظ إن تغيير الـ Status جزء من الـ Lifecycle نفسه.

Filters وFolders وSegments

الفكرة ببساطة: لما البيانات تكبر، ما ينفعش تفضل تقلّب بإيدك. اعمل Filter منطقي واحفظه.

📌 فرق مهم

Conversation Filter بيشتغل على المحادثات. Contacts Segment بيشتغل على العملاء. الاتنين شبه بعض في فكرة “التجميع”، لكن البيانات اللي بتفلتر عليها مختلفة.

Agents vs Teams

🧑‍💻 Agent

👥 Team

مثال: Sales Team / Billing Team / Support Team.
🛡️ Custom Role

حسب الـ plan والنسخة المتاحة، ممكن تحتاج Role مخصص لصلاحيات أدق.

🏷️ Label

تصنيف تشغيلي. مثال: VIP، Price Inquiry، Complaint، Hot Lead.

💡 الـ Label مش مجرد لون

أحسن Label هو اللي يدخل في قرار: Filter؟ Report؟ Routing؟ Automation؟ لو ملوش استخدام، ما تزودش Labels عالفاضي.

Custom Attributes

لما Labels ما تكفيش، استخدم بيانات منظمة. مثال:

Contact Attributes\nplan = Enterprise\ncity = Dubai\nlanguage = Arabic\n\nConversation Attributes\nlead_source = Meta Ads\nproject = DAMAC Island\nbudget = 1500000

المبدأ هنا: Label بتقول “التصنيف إيه؟”، بينما Attribute يقدر يحمل “القيمة إيه؟”.

Automation: خَلّي Chatwoot يشتغل معاك

دي أهم حصة في الجزء التشغيلي. هنا هنفك Automation Rule إلى ٣ أجزاء: Event + Conditions + Actions، ونعمل Routing حقيقي بدل Automation شكلها حلو بس.

↳ القصة: لما الشغل يزيد، نخلي Chatwoot ينفذ القرارات المتكررة بدل الموظف.

⚙️ Actions
يعمل إيه؟
// سيناريو تدريبي\nEVENT: Conversation Created\nCONDITION: Message contains "سعر"\nACTION 1: Add Label = price_inquiry\nACTION 2: Assign Team = Sales\nACTION 3: Set Priority = High
🧠 الطريقة الصح للتفكير

Event = إيه اللي شغّل القاعدة؟ Conditions = إمتى القاعدة تنطبق؟ Actions = نعمل إيه لما الشروط تتحقق؟ لو فهمت التلاتة، أنت فهمت قلب Automation.

3 Rules لازم تتمرن عليهم

💰 Price Inquiry

Conversation Created → message contains “سعر” → Label + Sales Team + High Priority.

⭐ VIP

Contact/Attribute مناسب → Label VIP + Team مخصص + أولوية أعلى.

🧾 Billing

كلمات زي invoice / refund / payment → Billing Team + billing label.

⚠️ راقب الـ Loops

لو Rule بتعمل Action يولّد Event من نفس النوع اللي القاعدة بتراقبه، ممكن تدخل في loop. اختبر Rule على بيانات تجريبية، وخلي شروطك Tight ومحددة.

Macros vs Canned Responses vs Automation

⚡ Macro

Action sequence يدوي. الموظف يضغط ويشغل كذا خطوة مع بعض.

“ضغطت Macro → Label + Assign + Status”.
💬 Canned Response

رد نصي جاهز لتوفير وقت الكتابة وتوحيد أسلوب الفريق.

مثال: /welcome
🤖 Automation Rule

Rule تلقائية مبنية على Event + Conditions + Actions.

“كل مرة يحصل X، اعمل Y”.

Business Hours + SLA + CSAT

دي مش 3 Features منفصلة في دماغك. شوف العلاقة:

Business Hours→Expected Availability→SLA Timing→Reports→CSAT

الفكرة العملية: الشركة تقول “هنرد في خلال 30 دقيقة وقت العمل”. الـ SLA يقيس. والـ Reports تقول حصل إيه. والـ CSAT يقول العميل حس بإيه.

Webhook vs API

🔔 Webhook

مثال: message_created → n8n Webhook.
📡 API

Systemك → Chatwoot. أنت تبعت Request علشان تعمل أو تجيب حاجة.

مثال: n8n يرسل outgoing message.

Payload تفهمه مش تحفظه

كل Webhook بيجيب معاه بيانات. أهم مهارة إنك تبص على الـ JSON وتعرف تستخرج اللي محتاجه.

// مثال تعليمي مبسط، راجع payload الفعلي في حسابك/إصدارك\n{\n "event": "message_created",\n "conversation": {\n "id": 123\n },\n "message_type": "incoming",\n "content": "عايز أعرف السعر"\n}
event

اسم الحدث اللي حصل.

conversation.id

المحادثة اللي حصل فيها الحدث.

message_type

نوع الرسالة.

content

محتوى الرسالة.

sender

مين بعت حسب الـ payload المتاح.

account / inbox

السياق اللي حصل فيه الـ Event.

API عمليًا بـ Postman

جيب Access Tokenالتوكن يمثل صلاحيات الحساب/المستخدم حسب طريقة الاستخدام.
حدد Endpointاختار العملية اللي عايز تعملها من Application API.
جهّز HeadersAuth + Content-Type حسب الـ endpoint.
جهّز Body بصيغة JSONحط الرسالة أو البيانات المطلوبة.
Send ثم اقرأ Responseما تعتبرش الـ Request نجح إلا لما تفهم الـ Response والـ Status Code.
// هيكل تدريبي عام\nPOST /api/.../conversations/.../messages\nHeaders:\n api_access_token: YOUR_TOKEN\n Content-Type: application/json\n\nBody:\n{\n "content": "Hello",\n "message_type": "outgoing"\n}

المسار الدقيق للـ endpoint والـ parameters لازم تتأكد منه من API Reference الخاصة بنسخة Chatwoot اللي شغال عليها. الكود هنا تعليمي لتفهم شكل العملية، مش بديل عن الـ official docs.

Workflow بالتفصيل

1. Customer sends messageرسالة: “عايز سعر المشروع”.
2. Chatwoot receives itConversation موجودة في Inbox.
3. Webhook يطلع Eventn8n تستقبل الـ payload.
4. n8n تعمل Routingتقرأ account / inbox / message / attributes وتقرر المسار.
5. AI Agent يفهميستخدم Knowledge Base أو Logic مناسب.
6. قرار: Answer أو Handoffلو سؤال بسيط → Reply. لو محتاج بشر → Handoff.
7. n8n يكتب النتيجة في Chatwootبـ API Request أو الـ integration المناسب.
8. سجل وراقبLogs + status + labels + CRM/Sheets عند الحاجة.

Handoff من AI للموظف 🙋

أهم حاجة في الـ AI Support مش إنه يرد 100% لوحده. أهم حاجة يعرف إمتى ما ينفعش يكمّل.

// مثال Logic تعليمي\nIF customer_requests_human == true\nOR confidence < threshold\nOR issue_is_sensitive == true\nTHEN\n add_label("human_handoff")\n assign_team("Support")\n add_private_note("AI handed off with context")\n set_status("open")
🎯 قاعدة ذهبية

الـ AI الجيد مش اللي بيجاوب على كل حاجة. الجيد هو اللي يعرف حدوده، ويسلّم الحالة للبشر من غير ما العميل يبدأ الحكاية من الصفر.

Multi-Company Architecture 🏢

لو هتبيع النظام لأكثر من شركة، ما تبنيش workflow مفروض على الجميع. خليه يقرأ Account Context ويمرر الطلب للـ configuration المناسبة.

فكرة الـ Multi-Tenant: Workflow واحد ممكن يتعامل مع شركات مختلفة، لكن كل شركة لها بياناتها وقنواتها وموظفيها وقواعدها. التصميم النهائي لازم يمنع تسريب أو خلط بيانات الشركات.

Session ID وMemory

لو الـ AI محتاج Memory، اربط الـ session بالسياق الصحيح. مثال شائع في نظام محادثات:

Session ID = conversation.id\n\n// النتيجة\nكل Conversation ليها سياق منفصل\nما تخلطش ذاكرة عميل مع عميل تاني
🛡️ Security First

ما تحطش API tokens أو secrets داخل الـ frontend أو في GitHub. خزنها في Credentials/Environment Secrets حسب البنية اللي شغال بها.
